1. The Problem: More Data Than Threads

Imagine you have an array of one million floating-point numbers, and you need to double every element. In a sequential C program, you would write a simple for loop that iterates from index 0 to 999,999. The CPU executes one iteration at a time (ignoring vectorization and pipelining for now), processing each element in order.

A GPU, on the other hand, can launch thousands of threads simultaneously. A modern NVIDIA GPU might support launching, say, 82,944 threads at once (1,024 threads per block × 81 blocks if we use all streaming multiprocessors). But one million is far more than 82,944. So here lies our central question:

Central Question
If we have N data elements but can only launch T threads (where T < N), how does each thread know which elements it should process, and how do we ensure every element gets processed exactly once?

The answer is the grid-stride loop — one of the most important patterns in CUDA programming. By the end of this chapter, you will understand it so thoroughly that it becomes second nature.

2. Prerequisites — The CUDA Execution Model

Before diving into grid-stride loops, let us make sure we share a common understanding of how CUDA organizes parallel work. If you already know what blocks, grids, threadIdx, and blockIdx mean, feel free to skim this section.

2.1 Threads, Blocks, and Grids

CUDA organizes parallel execution in a three-level hierarchy:

  1. Thread — The smallest unit of execution. Each thread runs the same kernel function but can follow different code paths based on its unique identity.
  2. Block (also called a thread block) — A group of threads that can cooperate with each other through shared memory and synchronization barriers. A block can contain up to 1,024 threads.
  3. Grid — The collection of all blocks launched by a single kernel call. A grid can contain millions of blocks.
Analogy: A Factory
Think of a grid as a factory. The factory contains multiple workshops (blocks). Each workshop has a team of workers (threads). Workers within the same workshop can talk to each other and share tools (shared memory). Workers in different workshops cannot directly communicate during work.

Each of these can be organized in 1D, 2D, or 3D. For example:

  • A 1D block is a line of threads (like workers standing in a row).
  • A 2D block is a rectangle of threads (like workers arranged on a floor grid).
  • A 3D block is a volume of threads (like workers in a multi-story building).

Similarly, the grid of blocks can itself be 1D, 2D, or 3D.

Figure 2.1 — A grid containing 3 blocks, each with 6 threads (2×3). Each block has its own shared memory.

2.2 The Built-in Variables

Inside every CUDA kernel, every thread can access special built-in variables that tell it who it is and how big the grid is:

Variable Type Meaning
threadIdx.x/y/z uint3 This thread's position within its block
blockIdx.x/y/z uint3 This block's position within the grid
blockDim.x/y/z dim3 The size of each block (number of threads per block in each dimension)
gridDim.x/y/z dim3 The size of the grid (number of blocks in each dimension)

These four variables are the building blocks from which we derive the global thread ID — the unique identifier that lets each thread know which data element(s) to work on.

3. The Naïve Approach and Its Limitations

The simplest way to map threads to data is the one-thread-per-element approach. You launch exactly as many threads as you have data elements: 

__global__ void doubleElements(float* A, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) {
        A[i] = A[i] * 2.0f;
    }
}

// Host launch:
int threadsPerBlock = 256;
int numBlocks = (N + threadsPerBlock - 1) / threadsPerBlock;  // ceiling division
doubleElements<<>>(d_A, N);

Let us unpack this code visually. Suppose N = 10 and we choose threadsPerBlock = 4. The ceiling division gives us numBlocks = (10 + 3) / 4 = 3 blocks, for a total of 12 threads — just enough to cover all 10 elements (with 2 "spare" threads that do nothing).

Figure 3.1 — Complete anatomy of the naïve one-thread-per-element kernel. N = 10, threadsPerBlock = 4, numBlocks = 3 (12 total threads). Each thread computes a unique global ID. Threads with i ≥ N (the red dashed boundary) skip the work. The last two threads in Block 2 are wasted.

This works perfectly for small to moderate values of N. But it has several problems:

  1. Maximum grid size limit. CUDA limits gridDim.x to 2,147,483,647 (231 − 1) for compute capability 3.0+, but older hardware or the y/z dimensions have much smaller limits (65,535). If your data is too large, you simply cannot launch enough blocks.
  2. Occupancy waste. Launching exactly N/256 blocks might not align well with the GPU's streaming multiprocessors (SMs). You might launch too many blocks, causing scheduling overhead, or you might not launch enough to keep the GPU busy during memory stalls.
  3. Inflexibility. The kernel only works when each thread processes exactly one element. If you later want to do serial work within each thread (for better instruction-level parallelism or to reduce launch overhead), you need to rewrite the kernel.
  4. Debugging difficulty. With the one-thread-per-element pattern, you cannot easily run the kernel with a single thread or a single block to debug it, because changing the launch configuration changes which elements get processed.
Why Not Just Launch Enough Threads?
For an array of 10 billion elements, the naïve approach requires ~39 million blocks (at 256 threads each). While this is within limits for the x-dimension on modern GPUs, it creates enormous scheduling overhead. A grid-stride loop lets you use a reasonable number of blocks — say, a few thousand — and still cover all 10 billion elements.

4. The Grid-Stride Loop — Core Idea

The grid-stride loop solves all of the above problems with an elegantly simple idea:

The Grid-Stride Loop Pattern

Each thread starts at its unique global index. Then, instead of stopping after processing one element, the thread jumps forward by the total number of threads in the entire grid and processes the next element. It repeats this until it has walked past the end of the data.

4.1 The Formula

For a 1D grid-stride loop, the pattern is: 

int index  = blockIdx.x * blockDim.x + threadIdx.x;   // global thread ID
int stride = blockDim.x * gridDim.x;                   // total threads in grid

for (int i = index; i < N; i += stride) {
    // process element A[i]
}

Let us dissect each piece:

  • index — The starting position for this thread. Each thread gets a unique starting position from 0 to (total threads − 1).
  • stride — The total number of threads in the entire grid. This equals blockDim.x × gridDim.x (threads per block times number of blocks).
  • The for loop — Starting at index, the thread jumps forward by stride each iteration, processing elements at positions index, index + stride, index + 2×stride, and so on.

4.2 A Complete Walkthrough — The "Bucket Brigade" Analogy

Analogy: The Bucket Brigade

Imagine you have 30 buckets of water lined up in a row, and you have 12 firefighters. You could assign firefighter #0 to bucket #0, firefighter #1 to bucket #1, and so on. But you only have 12 firefighters, not 30!

With a grid-stride approach, each firefighter starts at their number, empties that bucket, then jumps ahead by 12 (the total number of firefighters):

  • Firefighter 0 handles buckets: 0, 12, 24
  • Firefighter 1 handles buckets: 1, 13, 25
  • Firefighter 2 handles buckets: 2, 14, 26
  • …
  • Firefighter 5 handles buckets: 5, 17, 29
  • Firefighter 6 handles buckets: 6, 18 (no 30—we're done!)
  • …
  • Firefighter 11 handles buckets: 11, 23 (no 35—we're done!)

Every bucket gets emptied exactly once, and no firefighter sits idle until all buckets up to their last one are covered.

5. 1D Grid-Stride Loops — Lines of Threads

The 1D case is the most common and the easiest to understand. Here, both the grid and the blocks are one-dimensional: a line of blocks, each being a line of threads.

5.1 Visual Walkthrough

Let us work through a concrete example. Suppose we have:

  • N = 20 data elements (indices 0 through 19)
  • 3 blocks (gridDim.x = 3)
  • 4 threads per block (blockDim.x = 4)
  • Therefore, total threads = 12, and the stride = 12
Figure 5.1 — A 1D grid with 3 blocks of 4 threads each, producing 12 unique global IDs (0–11).

Now let us see how these 12 threads cover all 20 data elements using a grid-stride loop:

Figure 5.2 — Grid-stride loop with 12 threads processing 20 elements. Each color represents threads from a different block. Pass 1 covers elements 0–11, Pass 2 covers 12–19. Threads 8–11 exit the loop in Pass 2 because their indices (20–23) exceed N.

5.2 Code Pattern

Here is the complete, production-quality 1D grid-stride loop kernel: 

__global__ void processArray(float* A, int N) {
    // Step 1: Compute this thread's unique global ID
    int index = blockIdx.x * blockDim.x + threadIdx.x;

    // Step 2: Compute the stride (total number of threads in the grid)
    int stride = blockDim.x * gridDim.x;

    // Step 3: Grid-stride loop
    for (int i = index; i < N; i += stride) {
        A[i] = A[i] * 2.0f;  // or whatever processing you need
    }
}

// Host-side launch: choose a sensible number of blocks
int threadsPerBlock = 256;
int numBlocks = 128;  // NOT (N + 255) / 256!
processArray<<>>(d_A, N);
Key Observation
Notice that numBlocks is a fixed, moderate number — not derived from N. The grid-stride loop lets us decouple the launch configuration from the data size. You can tune numBlocks for your specific GPU without worrying about the data size.

Why Does This Guarantee Full Coverage?

The threads have starting indices 0, 1, 2, …, stride−1. Every integer from 0 to stride−1 is covered. By jumping by stride, each thread covers a different residue class modulo stride. The union of all residue classes mod stride covers every non-negative integer. Since the loop stops at N, every index from 0 to N−1 is visited exactly once.

6. 2D Grid-Stride Loops — Rectangles of Threads

When working with 2D data — most commonly matrices or images — it is natural to use a 2D grid of 2D thread blocks. Instead of a single global index, each thread has two coordinates: x (column) and y (row).

6.1 Coordinate Computation

In a 2D grid-stride loop, we compute two independent global indices and two independent strides: 

// Global column index and stride
int col   = blockIdx.x * blockDim.x + threadIdx.x;
int col_s = blockDim.x * gridDim.x;

// Global row index and stride
int row   = blockIdx.y * blockDim.y + threadIdx.y;
int row_s = blockDim.y * gridDim.y;

The x-dimension maps to columns, and the y-dimension maps to rows. This is a convention — you could swap them, but this is the most common choice and aligns with how CUDA coalesces memory accesses for row-major matrices.

6.2 Visual Walkthrough

Consider a 2D grid with:

  • Grid: 2×2 blocks (gridDim = (2, 2))
  • Block: 3×2 threads (blockDim = (3, 2))
  • Matrix: 10 columns × 7 rows

Total threads in x: 2 × 3 = 6 (stride_x = 6). Total threads in y: 2 × 2 = 4 (stride_y = 4).

Figure 6.1 — 2D grid-stride loop. The first pass (rows 0–3) uses direct thread IDs. Rows 4–6 (shown lighter) are covered when threads add stride_y=4 to their row index. Similarly, columns 6–9 are covered when threads add stride_x=6 to their column index.

6.3 Code Pattern

__global__ void processMatrix(float* M, int width, int height) {
    // Column index and stride
    int col   = blockIdx.x * blockDim.x + threadIdx.x;
    int col_s = blockDim.x * gridDim.x;

    // Row index and stride
    int row   = blockIdx.y * blockDim.y + threadIdx.y;
    int row_s = blockDim.y * gridDim.y;

    // Nested grid-stride loops — one for each dimension
    for (int r = row; r < height; r += row_s) {
        for (int c = col; c < width; c += col_s) {
            int idx = r * width + c;       // row-major linear index
            M[idx] = M[idx] * 2.0f;
        }
    }
}

// Host-side launch
dim3 threadsPerBlock(16, 16);   // 256 threads total per block
dim3 numBlocks(8, 8);           // 64 blocks → 16,384 total threads
processMatrix<<>>(d_M, width, height);

7. 3D Grid-Stride Loops — Volumes of Threads

The 3D case extends the pattern one more time. This is used for volumetric data such as:

  • 3D medical imaging (CT scans, MRI volumes)
  • Computational fluid dynamics (CFD) grids
  • 3D textures in graphics
  • Tensor operations in deep learning

7.1 Coordinate Computation

// X dimension
int x   = blockIdx.x * blockDim.x + threadIdx.x;
int x_s = blockDim.x * gridDim.x;

// Y dimension
int y   = blockIdx.y * blockDim.y + threadIdx.y;
int y_s = blockDim.y * gridDim.y;

// Z dimension
int z   = blockIdx.z * blockDim.z + threadIdx.z;
int z_s = blockDim.z * gridDim.z;

7.2 Visual Walkthrough

Figure 7.1 — A single 3D thread block is a "box" of threads addressed by (threadIdx.x, threadIdx.y, threadIdx.z). The grid is a 3D array of such boxes. The same stride formula applies independently in each dimension.

7.3 Code Pattern

__global__ void processVolume(float* V, int W, int H, int D) {
    int x   = blockIdx.x * blockDim.x + threadIdx.x;
    int y   = blockIdx.y * blockDim.y + threadIdx.y;
    int z   = blockIdx.z * blockDim.z + threadIdx.z;

    int sx  = blockDim.x * gridDim.x;
    int sy  = blockDim.y * gridDim.y;
    int sz  = blockDim.z * gridDim.z;

    for (int iz = z; iz < D; iz += sz) {
        for (int iy = y; iy < H; iy += sy) {
            for (int ix = x; ix < W; ix += sx) {
                int idx = iz * H * W + iy * W + ix;
                V[idx] = someComputation(V[idx]);
            }
        }
    }
}

// Host launch
dim3 threadsPerBlock(8, 8, 4);     // 256 threads per block
dim3 numBlocks(4, 4, 4);           // 64 blocks
processVolume<<>>(d_V, W, H, D);

7.4 Volumetric Data Example

Suppose we are processing a 512 × 512 × 256 CT scan volume. With the launch configuration above:

  • Total threads in x: 8 × 4 = 32, stride_x = 32. Need to cover 512 → each thread handles 512/32 = 16 x-positions.
  • Total threads in y: 8 × 4 = 32, stride_y = 32. Each thread handles 16 y-positions.
  • Total threads in z: 4 × 4 = 16, stride_z = 16. Each thread handles 256/16 = 16 z-positions.
  • Each thread processes 16 × 16 × 16 = 4,096 voxels.
  • Total: 16,384 threads × 4,096 voxels = 67,108,864 = 512 × 512 × 256. ✓

8. Why Grid-Stride Loops Are Superior

Now that you understand the mechanics, let us examine why this pattern is universally recommended over the naïve one-thread-per-element approach.

8.1 Scalability

A grid-stride loop works correctly regardless of the relationship between the number of threads and the data size:

Scenario Threads = N Threads < N Threads > N
Naïve approach ✓ Works ✗ Misses elements! ✓ Works (waste)
Grid-stride loop ✓ Works (1 iter each) ✓ Works (multiple iters) ✓ Works (some skip loop)

8.2 Performance Tuning

With a grid-stride loop, you can independently tune the number of blocks and threads per block for maximum occupancy on your specific GPU, without changing the kernel code. For example: 

// Use CUDA occupancy calculator to find optimal launch config
int minGridSize, bestBlockSize;
cudaOccupancyMaxPotentialBlockSize(
    &minGridSize, &bestBlockSize, processArray, 0, N);
processArray<<>>(d_A, N);

The occupancy calculator suggests the launch configuration that maximizes the number of active warps on the GPU. Because the grid-stride loop handles any N, this configuration works perfectly regardless of data size.

8.3 Debugging and Testing

During development, you can launch a kernel with just one thread: 

// Debug launch: single thread processes ALL elements sequentially
processArray<<<1, 1>>>(d_A, N);

Because the stride is 1×1 = 1, this single thread iterates through every element, just like a CPU for loop. This makes it trivial to:

  • Set breakpoints and step through the kernel
  • Print debug output without interference from other threads
  • Compare GPU results against a known CPU reference implementation
  • Isolate race conditions by eliminating parallelism

8.4 Memory Coalescing

Memory Coalescing

When adjacent threads (within a warp of 32 threads) access adjacent memory addresses, the GPU hardware can combine these into a single wide memory transaction. This is called coalescing, and it is one of the most important performance considerations in CUDA.

Grid-stride loops naturally produce coalesced memory access patterns. In iteration k, adjacent threads access:

  • Thread 0: A[0 + k × stride]
  • Thread 1: A[1 + k × stride]
  • Thread 2: A[2 + k × stride]
  • …
  • Thread 31: A[31 + k × stride]

These are 32 consecutive addresses — perfectly coalesced! The alternative (giving each thread a contiguous chunk) would have adjacent threads accessing addresses far apart, destroying coalescing.

Figure 8.1 — Grid-stride vs. chunk-based memory access. In the grid-stride pattern, a warp's threads touch adjacent addresses (coalesced). In the chunk-based pattern, each thread "owns" a contiguous range, so simultaneous accesses are far apart (uncoalesced).

9. Common Pitfalls and Debugging Tips

9.1 Pitfall: Forgetting the Bounds Check

The i < N condition in the loop is critical. Without it, threads will access memory beyond the array, causing undefined behavior or crashes: 

// WRONG — no bounds check!
for (int i = index; ; i += stride) {   // infinite loop if stride > 0
    A[i] = A[i] * 2.0f;                // out-of-bounds access!
}

// CORRECT
for (int i = index; i < N; i += stride) {
    A[i] = A[i] * 2.0f;
}

9.2 Pitfall: Using int for Very Large Arrays

If N exceeds 231 − 1 (about 2.1 billion), a 32-bit int will overflow. Use long long or size_t: 

__global__ void processHugeArray(float* A, long long N) {
    long long index  = (long long)blockIdx.x * blockDim.x + threadIdx.x;
    long long stride = (long long)blockDim.x * gridDim.x;

    for (long long i = index; i < N; i += stride) {
        A[i] = A[i] * 2.0f;
    }
}

9.3 Pitfall: Choosing Too Few Blocks

While the grid-stride loop is correct with any number of blocks, using too few can leave SMs idle. A good rule of thumb: 

// At least enough blocks to fill all SMs
int deviceId;
cudaGetDevice(&deviceId);
cudaDeviceProp props;
cudaGetDeviceProperties(&props, deviceId);

int numBlocks = props.multiProcessorCount * 2;  // 2× SMs is a good start

9.4 Pitfall: Mixing Up Dimensions in 2D/3D

A common mistake in 2D kernels is computing the row from blockIdx.x and the column from blockIdx.y (or vice versa), then computing the linear index as row * width + col. This works mathematically, but if the mapping is not consistent with how data is stored in memory, it destroys coalescing.

Convention
For row-major matrices (the default in C/C++), map x → column and y → row. This ensures that adjacent threads in the x-dimension (which form warps) access adjacent columns — which are adjacent in memory for a given row.

9.5 Debugging Technique: printf in Kernels

__global__ void debugKernel(float* A, int N) {
    int index  = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = blockDim.x * gridDim.x;

    for (int i = index; i < N; i += stride) {
        printf("Thread %d (block %d, local %d) processing A[%d]\n",
               index, blockIdx.x, threadIdx.x, i);
        A[i] = A[i] * 2.0f;
    }
}

// Launch with very few threads for readable output
debugKernel<<<2, 3>>>(d_A, 10);
cudaDeviceSynchronize();

11. Summary

The grid-stride loop is a deceptively simple pattern that solves a fundamental problem in GPU programming: how to map a fixed number of threads to an arbitrarily large dataset. Let us recap what we have learned:

  1. The Problem: GPUs have a finite number of threads, but datasets can be arbitrarily large.
  2. The Solution: Each thread starts at its unique global ID, then jumps forward by the total number of threads (the "stride"), processing one element per jump, until it has walked past the end of the data.
  3. The Formula: for (int i = globalID; i < N; i += totalThreads)
  4. Dimensionality: The same pattern extends naturally to 2D (nested loops with x/y strides) and 3D (triple-nested loops with x/y/z strides).
  5. Benefits: Works for any N, enables occupancy tuning, produces coalesced memory access, and supports serial debugging.
The One Formula to Remember

Global ID = blockIdx × blockDim + threadIdx

Then stride by gridDim × blockDim in each dimension.

With this single pattern in your toolkit, you can write CUDA kernels that are correct, efficient, debuggable, and portable across GPU generations. It is the first pattern every CUDA programmer should learn, and it remains useful throughout one's entire career in GPU computing.
